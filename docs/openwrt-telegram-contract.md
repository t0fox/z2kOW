# Контракт Telegram для OpenWrt

> **Статус: рабочая сборка.** Прозрачный Telegram-прокси включён в текущий OpenWrt-стек z2kOW. Доступность определяется состоянием конкретных маршрутов и условиями сети; успешное открытие WebSocket не означает подтверждённого ответа Telegram.

## Назначение и границы

**Telegram в OpenWrt — прозрачный локальный MTProto → WebSocket Secure (WSS) прокси на Rust.** Клиентам в LAN не нужны ссылки, QR-коды, секрет MTProxy или ручное включение proxy. Проект не предоставляет внешний VPS/relay и не требует WARP для этого пути.

- `platform/openwrt/tg.sh` отвечает за OpenWrt-адаптацию.
- `platform/openwrt/tg-proxy/` — исходники локального Rust-процесса.
- procd управляет **одним** экземпляром на локальном порту `1443`.
- nftables перенаправляет только выбранный Telegram TCP-трафик, включая MTProto DC и media DC, сохраняя исходный адрес назначения для `SO_ORIGINAL_DST`.
- Rust использует WSS-назначения с предусмотренным Cloudflare/upstream fallback и **не отключает** проверку TLS-сертификатов.
- Исходящие сокеты Rust помечаются так, чтобы не перехватывать собственные подключения.
- Используется существующая runtime-таблица nftables, а не второй независимый firewall.

Старый Go-клиент, пользовательские `relay URL/secret` и отдельный слушатель `1444` не принадлежат текущему OpenWrt-решению.

## Адреса назначения и отказ

Сопоставление входящего `original_dst` со снимком Telegram DC — часть механизма безопасности и точности маршрутизации. Отсутствующий в актуальном снимке адрес может вызвать отказ `AddressNotListed`; **ошибку нельзя объявлять успешным подключением** или обходить случайной подменой адреса.

При разборе такого инцидента отдельно проверяются актуальность карты DC, nftables-наборы и попадание соединений через conntrack. Отказ внутри Rust сам по себе не доказывает, почему конкретный адрес пришёл на локальный listener. Исторический снимок nft/conntrack нужен для установления полной причинной цепочки.

HTTP/CDN-трафик, включая TCP/80, **не** должен пересылаться как MTProto по WebSocket. Media DC, принадлежащие MTProto, не следует путать с обычными HTTP CDN; последние обслуживаются только независимыми механизмами маршрутизации.

## Лимит соединений и память

- Режим `Auto` по умолчанию имеет программный предел **32 одновременных слота** с учётом доступной памяти и лимита файловых дескрипторов.
- Auto резервирует 20% допустимых FD и 32 служебных дескриптора, учитывает до 5 FD на слот, оставляет запас по `MemTotal/MemAvailable` и закладывает 1 МиБ на слот.
- `Manual` принимает настройку 1–128, но фактический предел всё равно ограничивается вычисленным безопасным бюджетом.
- Если метрики некорректны или безопасный бюджет равен нулю, включать перенаправление нельзя.

Операторские значения в `/etc/z2k/tg-policy.conf`:

~~~sh
TG_CONNECTION_MODE=auto
TG_CONNECTION_LIMIT=32
~~~

Эти значения сохраняются при регенерации общего конфига. Локальные WSL-замеры повлияли на первоначальные ограничения, но **не являются замерами потребления ресурсов физического роутера**.

## Архитектуры и обновление

Матрица Rust-сборок включает семь семейств: `arm64`, `arm` (ARMv5 soft-float), `x86_64`, `x86`, `mips`, `mipsel`, `riscv64`. Точное соответствие OpenWrt ABI и Rust target описано в [`tg-rust-targets.tsv`](../platform/openwrt/tg-rust-targets.tsv). На неподдерживаемом ABI Telegram-функция должна показывать «Тип не поддерживается», не запускать несовместимый бинарник и не возвращаться к старому VPS-пути.

Обновление использует общий подписанный rootfs, проверку ABI и `install_release(tag)` с rollback. Нужные настройки и состояние пользователя сохраняются. Старые Telegram/VPS-службы нового релиза не должны запускаться; снятие legacy-файлов не должно удалять несвязанные настройки.

## Выбор маршрутов, диагностика и восстановление

- Основной путь использует официальный Telegram WSS вида `wss://kwsN.web.telegram.org/apiws` для соответствующего DC.
- При отказе прямого WSS используются настроенные Cloudflare Worker, резервный Cloudflare proxy с пулом доменов и прямой TCP fallback. Политика `adaptive` учитывает измеренную доступность и задержки, неудачные маршруты временно исключаются.
- Telegram WSS и Cloudflare proxy требуют кадрирования по MTProto-пакетам; Cloudflare Worker передаёт непрерывный TCP-поток, разбитый на WebSocket-кадры.
- По умолчанию доступен резервный пул Cloudflare proxy; собственные Worker-домены настраиваются отдельно и не обязательны для прямого маршрута.
- Активная диагностика DC1–DC5 проверяет отдельные этапы соединения вплоть до ответа MTProto `req_pq_multi/resPQ`. Ошибки отображаются с причиной и этапом отказа. Наличие работающего listener ещё не означает доступность всех DC.
- CI и синтетические проверки не гарантируют одинаковую работу у всех провайдеров и на любом роутере; при неполадках проверяйте актуальную карту DC, состояние маршрутов и логи.
