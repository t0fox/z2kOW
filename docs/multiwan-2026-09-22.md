# Automatic WAN discovery across Keenetic policy tables

A user with USB-modem and Wi-Fi uplinks reports that YouTube works only after
one provider is disabled. This report is consistent with incomplete WAN rule
coverage, but its cause has not been confirmed on that user's router.

Previously, the firewall detected defaults only in the main routing table.
Two defaults in main already worked; a second provider in a separate policy
table, or an ECMP continuation nexthop, could be omitted. The self-healer checked
chain/protocol coverage across the whole family and could overlook that WAN.

`lib/wan.sh` now supplies a shared, read-only detector to the firewall and its
self-healer. It reads defaults from all tables (main fallback if unsupported),
handles ECMP continuations and excludes unreachable/blackhole routes, failed
nexthops, LAN bridges, loopback, and z2k relay/WARP devices and tables. Duplicate
interfaces are removed. An explicit `WAN_IFACE` list continues to take priority.
No provider priorities, policy routing rules or user configuration are changed.
Native VPN interfaces carrying an actual default remain eligible, as before.

The scheduler now checks required NFQUEUE chain/protocol/interface combinations
for each discovered WAN. A missing secondary interface triggers the existing
settle/debounce/lock-protected additive `start_fw`, without a daemon restart or
firewall teardown. The NDM hook remains the immediate recovery path; the
scheduler is the periodic fallback (approximately once per minute). Rules for
an offline device are not actively removed by this additive repair.

Validation on 2026-09-22:

- Executable fixtures cover single WAN, policy-table USB WAN, IPv4/IPv6, ECMP,
  a failed ECMP sibling, duplicate defaults, main fallback, LAN and internal
  tunnel exclusions, and an explicit override.
- The self-healer repairs missing secondary-WAN rules despite a complete primary
  set; a complete dual-WAN set and a manual primary-only override do not repair.
- On the owner's single-WAN Keenetic, the detector returns `ppp0` for both
  families. After deploying the init, shared library and self-healer and running
  additive `start_fw`, before/after NFQUEUE rule dumps compare byte-for-byte.
  A self-healer run performs no repair. LAN HTTPS probes return 200 for YouTube
  and core.telegram.org, and the Telegram UDP-ready marker remains present.
- Full local CI passed (one existing macOS BSD-sed test skip). The final WAN
  and self-healing suites passed 13 and 33 checks respectively; shell lint passed.
- Live rollback copies: `/opt/z2k-multiwan-backup-20260922/`. The new library can
  remain unused when restoring the old init and self-healer.

There is no live dual-provider reproduction yet. HTTP 200 is a connection check,
not proof of sustained YouTube video playback. Different ISPs can require
different DPI strategies; ensuring both WANs receive rules does not guarantee
that the same strategy works on both. The reported user's fix remains to be
confirmed after trying this change. This change is not a public release yet.

Keenetic documents concurrent uplinks and policy routing:
https://support.keenetic.com/titan/kn-1811/en/17893.html
