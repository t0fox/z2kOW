# Карта вызовов и контрактов WARP для OpenWrt

Снимок исходной реализации перед переносом в Rust. Основной OpenWrt backend — `platform/openwrt/warp.sh`; `files/z2k-warp.sh` — отдельная прежняя реализация, на которую ещё ссылаются BDD-проверки. Go-пакет `z2k-warpd` остаётся владельцем туннеля и его протоколов.

## Входы и вызывающие стороны

| Вызов | Точка входа | Контракт |
|---|---|---|
| WebPanel lifecycle/status | `webpanel/cgi/actions.sh` | `install`, `enable`, `disable`, `restart`, `remove`, `license`, `ipset [--reconcile-rules]`, `migrate`, `status`; `license` получает ввод через stdin; `status` возвращает строку `key=value`, дополненную `enabled` и `wdtt`. |
| OpenWrt boot/procd | `platform/openwrt/files/etc/init.d/z2k` | В `start_service` интегрирует WARP с общим OpenWrt-сервисом; `z2k_ow_warp 1` собирает procd instance командой `z2k-warpd run`. procd остаётся владельцем процесса. |
| Cron health | `platform/openwrt/schedule.sh` → `platform/openwrt/warp-check.sh check` | Одноразовая проверка раз в минуту; не запускает демон, сводит маршрутизацию к proven-ready или fail-open. |
| Network/firewall events | init/hotplug → `platform/openwrt/warp.sh` (`rules`, `1`, `0`) | Повторное применение nft и безопасное восстановление после firewall/network/reboot. |
| Atomic engine refresh | `platform/openwrt/warp-proc.sh stop|start` | Stop обязан снять PBR до остановки старого PID и дождаться закрытия TUN; start ожидает ready ограниченно, procd повторно поднимает процесс. |
| Списки игр | `platform/openwrt/release.sh`, `files/z2k-update-lists.sh` | Релизные игровые списки хранятся в payload `lists/warp/games`; обновление вызывает `ipset` backend. Пользовательские списки и переключатели принадлежат `/etc/z2k/user-lists/warp`. |
| Удаление | `platform/openwrt/uninstall.sh` | Снимает принадлежащие WARP правила и бинарник, но сохраняет регистрацию в `/etc/z2k/state/warp/device.json` и пользовательские данные. |

## Функции текущего backend

`platform/openwrt/warp.sh` объединяет следующие зоны ответственности:

1. **Состояние и процессы:** Rust `config-read` читает `GAME_WARP_ENABLED`, `ENABLED`, `Z2K_WARP_TRANSPORT`, `Z2K_WARP_WDTT` без выполнения файла и сохраняет first/last-match и default; Shell fallback остаётся без ELF. Контроллер проверяет регистрацию, бинарник, procd/PID и JSON `ready`; собирает argv `z2k-warpd run --net-backend=external`; различает process bounce и полный disable.
2. **Списки и область политики:** при наличии Rust ELF `warp_lists_migrate` вызывает `list-migrate`, которая блокирует изменения, один раз удаляет только известные legacy aggregate-файлы, создаёт маркер и задаёт права `.txt`; без ELF остаётся исходный Shell fallback. Rust выбирает user/game-списки и scope (`policy-scope`), читает LAN/WireGuard интерфейсы из UCI (`interfaces`) и для LAN предпочитает активное `device` из `ubus`, с fallback на UCI `device`/`ifname`. Выбранные private/CGNAT IPv4 разрешаются из MAC, JSON-соседей `ip -4 -j neigh`, авторизованных hostapd клиентов и DHCP leases (`device-ips`). На Rust-архитектурах перечень и nft-синхронизация читаются модулем `lists`/`nft-sync`; Shell `warp_active_lists` и AWK-фильтр остаются в fallback без ELF.
3. **nftables:** атомарно заменяет destination/source sets одним `nft -f -` batch; создаёт и проверяет MARK/MSS/FWD/NAT цепи в принадлежащем другой подсистеме `inet zapret2`; ограничивает метку маской `0x80000000`; поддерживает WDTT, WG-client и временные пары client→IPv4. Ошибки nft проверяются, конфликтующие объекты не присваиваются WARP.
4. **DNS-наблюдатель:** `warp-domain.sh` делегирует чтение доменов и публикацию `domains.v1` командам `domains-list`/`domains-sync`, запись/сброс error marker — `domains-error`, создание и удаление nft-наборов/наблюдателя — `nft-domain-*`; Rust получает runtime LAN-интерфейсы через общий `interfaces lan`. Shell сохраняет procd-интеграцию и вызовы OpenWrt. Go-движок сохраняет существующий формат временных пар и TTL.
5. **Маршрутизация и готовность:** выделенная таблица `989`, mark-rule pref `500`, probe-rule pref `499`; до `ready` допускается только source-specific probe route. Rust читает inventory как JSON через `ip -4 -j rule show` и `ip -4 -j route show table all`; malformed snapshot, занятый priority, пересекающийся fwmark и чужой маршрут дают ошибку. Сначала снимается пользовательский policy, а маршрут удаляется только при совпадении owner record и точного default route `z2ktunN`. Изменения выполняются отдельными argv-вызовами `ip`, затем состояние перечитывается и проверяется.
6. **Восстановление и сериализация:** Rust `MutationLock` владеет lock lease, проверкой PID/start-time, ожиданием и stale recovery. Shell lifecycle/update entrypoints вызывают `lock-acquire`/`lock-release`; маркер supersede и вызовы procd остаются в OpenWrt glue. Cron-обновление игровых списков держит тот же lock на время загрузки и замены файлов, затем снимает его перед вызовом `ipset`, который берёт lock для своей мутации. `install_release` публикует transaction marker, останавливает службы, держит WARP lock только на время замены payload и освобождает его перед procd start/stop; cron и ручные команды видят marker и откладывают работу. Cron/hotplug и ручные вызовы разделяют один каталог lock; transient read errors не являются доказательством сломанного состояния. `z2k_ow_warp_check` отдельно проверяет маршрутные доказательства, а не только `status.json`.
7. **Установка/регистрация:** получает архитектурный бинарник из проверенного release payload, вызывает регистрацию через существующий движок, сохраняет user proxy только при явном выборе и не включает маршрутизацию при `install`.

## Стабильные внешние данные и ограничения

- Постоянные данные: `/etc/z2k/config`, `/etc/z2k/state/warp/device.json`, `/etc/z2k/user-lists/warp`; runtime: `/tmp/z2k/warp` и `/tmp/z2k-warp`; релизные списки: `/usr/lib/z2k/lists/warp`.
- WARP необязателен. Его отсутствие не должно блокировать установку, обновление или другие подсистемы.
- `disable` сначала снимает PBR, затем останавливает движок и меняет флаг. `install` не включает PBR. Отсутствие `ready` означает fail-open.
- `status` WebPanel — существующий `key=value`; daemon status JSON и `device.json` — принадлежащие Go-движку форматы, которые Rust не переписывает.
- Публичные точки списка также есть в `webpanel/cgi/actions.sh`: save/read/delete/toggle, game toggle, WDTT rollback при ошибке применения. Это часть UI-контракта и владелец операций должен быть сведен к одному backend без изменения API.
- Архитектурные артефакты Go заданы `build-matrix.tsv`; stage-rootfs сейчас требует 7 OpenWrt бинарников `z2k-warpd`. Новую поддержку Rust нельзя считать подтверждённой только по наличию target triple.

## Существующее покрытие перед миграцией

Основные группы: `tests/openwrt/test_ow_warp_{functional,lifecycle,status,fw4_forward,domain_paths,parity}.sh`, `tests/test_warp_*.sh`, `tests/test_panel_warp_ui.sh`, `tests/features/warp.feature`, install/upgrade/uninstall проверки. Значительная часть OpenWrt-тестов подменяет `nft`, `ip` или procd shell-стабами; они полезны для регрессии контрактов, но не доказывают работу с настоящими iproute2/nftables/procd и не заменяют требуемый QEMU acceptance.

`files/init.d/S51z2k-warp` и `files/z2k-warp.sh` — старые общие/Entware entrypoints; OpenWrt rootfs из `scripts/openwrt/stage-rootfs.sh` их не ставит. Миграция OpenWrt должна менять путь через `platform/openwrt/files/etc/init.d/z2k`, а не менять legacy init.

## Текущее состояние переноса

- Rust `runtime-observe` объединяет чтение Go `status.json`, процесса `z2k-warpd run` и наличия интерфейса через `ip -j link show`. Он различает `not-ready` и `unreadable`; Shell использует его в `_warp_proven_ready`. `state-observe` остаётся узкой командой для проверки самого JSON.
- Rust `health-plan` собирает конфигурацию с first/last-match, наличие бинарника и регистрации, process/status и `ip -j link show` в один выбор перехода: disabled, missing, process-absent, not-ready, ready или defer. Готовый переход возвращает iface из того же status-снимка; Shell не перечитывает его перед repair. Ошибки чтения `/proc`, config, status или iproute2 дают defer.
- Rust `boot-plan` отдельно решает, должен ли WARP участвовать в boot/hotplug: учитывает first-match WARP flag, last-match глобального `ENABLED`, executable бит Go engine и непустой device file. Ошибка чтения возвращает `defer`; OpenWrt Shell не снимает nft/PBR на временной ошибке состояния, а выполняет procd-вызов только после `wanted`.
- При `process-absent` Shell выполняет только OpenWrt/procd-восстановление: latch на одну попытку, проверка живой procd-регистрации и service rebuild. procd сохраняет владение `z2k-warpd`; Rust CLI не становится процессным supervisor.
- `z2k_ow_warp_check` передаёт Rust `policy-plan` три состояния: WARP-флаг, готовность Go-движка и наличие PBR. Исправное состояние даёт `noop`; ошибка чтения конфигурации, status, iproute2 или nft откладывает health tick без мутаций. Проверка процесса повторяется при первом сбое чтения. Явное `ready:false` и подтверждённо остановленный процесс по-прежнему ведут к fail-open teardown. При отсутствии Rust ELF сохраняется старый Shell-путь.
- `_warp_wait_ready` на Rust-пути использует `ready-observe-since`: контроллер проверяет Go-процесс, `status.json`, свежесть status относительно начала ожидания и существование интерфейса через `ip -j link show`. JSON и mtime относятся к одному открытому inode; concurrent rewrite откладывает решение, нулевой epoch отклоняется. Старый `ready` не принимается, transient read errors продолжают цикл ожидания. Shell сохраняет probe-route, supersession, таймер и procd glue; legacy путь без ELF прежний.
- Rust `nft-tun-apply` формирует и применяет одной атомарной транзакцией MSS/FWD/NAT-цепи для активного TUN. Shell вызывает отдельные `nft-fw4-forward-apply`, `nft-fw4-forward-verify` и `nft-fw4-forward-remove` для admission rule fw4; удаление пакетного wildcard include запрещено. При ошибке fw4 Shell просит Rust очистить TUN-цепи. Без установленного контроллера сохраняются прежние Shell batch и fw4 fallback.
- Rust `nft-chain-clear` читает таблицу и одним атомарным batch очищает только указанные непустые цепи. `_warp_tun_clear` и `_warp_mark_clear` делегируют очистку Rust; отсутствующая таблица или цепь и повторная очистка не вызывают nft-мутаций.
- FW4 runtime rule ownership также перенесён в Rust. `nft-fw4-forward-apply` атомарно вставляет точное или wildcard-совместимое правило, `verify` проверяет точное состояние, а `remove` одним batch удаляет только runtime `z2ktunN` handles с принадлежащим комментарием и сохраняет wildcard. Shell-функции оставлены как OpenWrt entrypoints и fallback без ELF.
- `nft-warp-remove` строит одну транзакцию для удаления известных WARP-цепей и, только при полном удалении, IP-наборов. `warp_nft_remove` делегирует Rust-удаление FW4 runtime rule, DNS-объектов и WARP-цепей/наборов; без контроллера остаётся legacy Shell путь.
- Rust `nft-mark-apply` и `nft-mark-verify` под общим WARP lock читают scope, домены, config WDTT и фактическое содержимое destination set, вычисляют `list_active`/`wdtt_active` и применяют правила одним атомарным batch. Ошибка чтения nft/config не превращается в пустую политику. Shell остаётся glue для LAN/WireGuard-интерфейсов и подготовки domain set/observer; без ELF остаётся прежний fallback.
- Rust `list-migrate` выполняет одноразовую очистку известных legacy aggregate-имён под общим и list lock; тесты проверяют сохранение пользовательского файла с таким именем после появления маркера. Установка CLI и fallback-путь проверены через реальный Shell entrypoint в WSL.
- На Rust-пути `warp_nft_sets_load` сразу вызывает `nft-sync`; старый Shell-парсер выполняется только в fallback без контроллера. Read-only `nft-sets-verify` в Rust различает совпадение (`ready=1`), подтверждённое несовпадение (`ready=0`) и ошибку чтения (ненулевой код без `ready=0`). Health-check откладывает tick при временной ошибке чтения set inventory и не снимает PBR/nft.
- Rust route inventory использует структурированный JSON iproute2; unit-тесты покрывают exact owner state, чужой route, пересечение fwmark, повреждённые mask и unrelated main route. `route-reconcile` сначала проверяет оба owner record, route и правила, а затем вызывает apply только при несовпадении; Shell health-check делегирует ему PBR repair и сохраняет fail-open обработку ошибки. `route-remove-owned` читает owner records внутри контроллера, удаляет только принадлежащую WARP политику и сохраняет чужие probe/PBR owner records и правила. WSL namespace и OpenWrt QEMU с текущим x86_64 ELF подтвердили применение и проверку PBR, повторный reconcile без мутаций и отказ при конфликте владельца. Legacy Shell fallback остаётся только для запуска без ELF.
- Rust `device-ips` перенёс разбор выбранных MAC/IP, `ip -4 -j neigh show`, авторизованного hostapd association и сроков DHCP lease. Ошибка чтения выбранных устройств, `ip neigh`, `ubus` или leases возвращается как ошибка и не превращается в пустой source set. Shell сохраняет исходный fallback без ELF.
- Rust `lock-acquire`/`lock-release` теперь управляет lock lease для Shell lifecycle и `warp-proc.sh`; owner хранит PID и start-time, умерший процесс можно безопасно удалить после SIGKILL. Shell fallback с mkdir-lock оставлен только для платформ без ELF.
- `files/z2k-update-lists.sh::update_warp_game_list` на OpenWrt загружает существующий `warp.sh` в source-only режиме и сериализует загрузку/замену/очистку игровых списков с ручными действиями и восстановлением. Повторное применение ipset выполняется после снятия lock. Во время install transaction updater и ручные команды отказываются от мутаций. WSL и OpenWrt QEMU проверили lock настоящим Rust CLI; QEMU cleanup дождался updater, а release lock helper корректно захватил и снял lease. Обычная проверка списков прошла 41/41.
- При установленном Rust `warp_domain_backend_ready` использует read-only `nft-domain-verify`: контроллер проверяет владение таблицей пар, observer-таблицей и обеими hook-цепями, а также NFLOG group в каждой цепи. Ошибка чтения nft возвращается как ошибка проверки, а не как готовое состояние; Shell fallback сохранён.
- Route error marker перенесён в `route-error-set`/`route-error-clear`: Rust берёт общий WARP lock, атомарно сохраняет первый `reason timestamp` с mode `0600` и идемпотентно чистит marker вместе с незавершёнными временными файлами. Shell wrapper сохраняет старый путь без ELF.
- Пользовательский op marker обслуживают `op-begin`, `op-current` и `op-clear`. Для него Rust берёт отдельную короткую блокировку до общего WARP lock; чтение ошибки не объявляет действие перебитым, а завершение снимает marker только при совпадении PID. Shell оставляет логирование supersede и fallback без ELF.
- Маркер одноразового восстановления procd обслуживают `procd-recovery-claim` и `procd-recovery-clear`: claim атомарен, сохраняет формат `attempted <epoch>` и возвращает ровно одного владельца при конкурентных cron/procd вызовах. Shell оставляет только запрос состояния ubus и rebuild сервиса; без ELF сохраняется прежний fallback.
- `service-plan` в Rust выбирает `rebuild`, `reload`, `none` или `defer` по намерению, прежнему флагу, состоянию процесса и tri-state наблюдению procd. `_z2k_ow_service_running` различает подтверждённые active/inactive и ошибку `ubus`/init; при ошибке Shell не считает службу выключенной и откладывает transition. Владение процессом и вызов init/reload/restart остаются у procd glue.
- `register-due` переносит проверку retry stamp из Shell в Rust и возвращает `due`, `wait` или `defer`. Missing/malformed stamp сохраняет прежний `due`; ошибки чтения откладывают новую регистрацию. Shell по-прежнему вызывает неизменённую команду `z2k-warpd register`; fallback без Rust также не регистрирует устройство при ошибке чтения stamp.
- Запись `GAME_WARP_ENABLED` из `warp_set_flag` делегируется `warp-flag-set`. Rust принимает только `0`/`1`, использует общий `.z2k-flaglock` контракт `set_flag`, атомарно сохраняет прочие настройки и при уже верном значении не мутирует файл; Shell сохраняет прежний путь без ELF.
- Запись `Z2K_WARP_WDTT` из WebPanel делегируется `config-flag-set` на Rust-пути и использует тот же атомарный флаговый lock; при ошибке применения nft-политики Shell восстанавливает прежнее значение через контроллер. Проверены допустимые значения, сохранение остальных настроек и rollback через реальный panel entrypoint в WSL.
- Rust `disable-state` под общим lock удаляет только принадлежащие owner records PBR-маршруты, принадлежащее fw4 runtime-правило, очищает WARP nft-цепи атомарным batch, сбрасывает domain-error marker и атомарно выключает `GAME_WARP_ENABLED`. `warp_disable` оставляет procd-маркеры, остановку/проверку процесса и service reload в Shell; если ELF отсутствует, выполняется старый путь.
- QEMU `qemu-warp-disable-remove.sh` запускает текущий `warp.sh` и Rust ELF с настоящими OpenWrt `nft`, `iproute2` и `procd`: сначала проверяет прямой `disable-state`, затем идемпотентный Shell `disable` и полное удаление WARP nft-объектов с сохранением registration/license/list файлов. Туннель и установленный сервис `z2k` в тесте не запускаются.
- CI собирает Rust ELF четырьмя ABI-группами, кэширует Cargo target и закреплённые linker SDK, запускает каждый вариант через QEMU-user и передаёт в rootfs job проверенные артефакты того же source SHA/run ID без повторной сборки.
- До текущих FW4/nft изменений сборка и запуск ELF через QEMU-user прошли для семи Rust ABI: ARMv5te soft-float, AArch64, x86_64, i686, MIPS BE, MIPS LE и riscv64. Финальная сборка source SHA `8626cec5852b51ea4b1585215908f4ef2438f5e3` также собрала и запустила все семь вариантов. Go ARMv7 target совместим с Rust `arm` ABI ARMv5te soft-float; физический ARMv7 роутер не проверялся. Go-матрица также содержит WARP `mips64le` и `ppc64`, для которых Rust target не заявлен и Shell fallback сохранён.
- Перенос остаётся частичным: Rust уже владеет plan/readiness решениями, lock lease, recovery marker и операциями со списками; OpenWrt Shell ещё координирует последовательность enable/disable/restart, регистрацию и rebuild instance через procd, а также lifecycle DNS-observer. Shell-парсер и обнаружение активных файлов остаются fallback без ELF; путь с Rust ELF использует `nft-sync`/`policy-scope`. Эти зоны нельзя считать перенесёнными одной командой `state-observe`.
- В OpenWrt 25.12.5 QEMU подтверждены реальные `iproute2` 6.18.0, `nftables` 1.1.6 и `procd` как PID 1. На одном из предыдущих x86_64-срезов controller nft test проверил восстановление блокировки после SIGKILL, атомарность и отказ при ошибках чтения; `qemu-warp-route.sh` подтвердил route apply/verify/remove, идемпотентность и точное владение. `runtime-observe` с реальным `/proc` гостя без Go-процесса вернул `not-ready absent`, сохранив fail-open. Реальный запуск Go WARP через procd, active tunnel recovery, network restart и reboot остаются незакрытыми проверками.
- На предыдущем x86_64-срезе OpenWrt QEMU проверил route apply/verify/remove; nft sets sync и verify на настоящем `nft`; mismatch дал `ready=0`, sync восстановил набор; domain-only список очистил IP sets; недоступный `nft` вернул ошибку, а не mismatch. Shell health-check под реальной ошибкой чтения наборов в WSL оставил route/nft неизменными.
- Подписанный полный install/update/WARP-remove/uninstall lifecycle прошёл на текущем x86_64 ELF `a7506cd1…` и текущем Shell payload в отдельном OpenWrt QEMU overlay. `p-86.18` обновлён через `p-86.19` до `p-86.20`, проверены общий lock во время updater, сохранность `device.json`, synthetic account/license/config/list sentinels, WARP remove и полный uninstall. Реальный Cloudflare registration и Go-туннель не запускались.
- Полная сборка source SHA `8626cec5852b51ea4b1585215908f4ef2438f5e3` ранее прошла для всех семи ABI из `rust-targets.tsv`; каждый бинарник запускался через QEMU-user. Это предыдущий source, а не текущая матрица. Go WARP-цели `mips64le` и `ppc64` не имеют production-ready Rust target, поэтому для них сохраняется Shell fallback.
