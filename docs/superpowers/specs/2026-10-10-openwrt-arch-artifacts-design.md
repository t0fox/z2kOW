# Архитектурные артефакты для установки OpenWrt

## Цель

На роутерах OpenWrt с 128 МБ RAM установщик должен скачивать и распаковывать только payload своей архитектуры. Установка, обновление и повторная установка остаются одним путём `install_release(tag)`. Существующие подпись манифеста, проверка содержимого, rollback, восстановление после незавершённой транзакции при загрузке, конфигурации, ownership и адаптация upstream z2k сохраняются.

Изменение не переводит проект на APK и не заменяет текущую транзакционную архитектуру.

## Релиз и манифест

Сборка создаёт семь детерминированных rootfs-архивов: `arm64`, `arm`, `x86_64`, `x86`, `mips`, `mipsel` и `riscv64`. Каждый включает общую часть rootfs и только одну архитектуру в трёх деревьях бинарников: `usr/lib/z2k/bin`, `usr/lib/z2k/platform/openwrt/bin` (WARP) и `opt/zapret2/binaries`. Наличие всех обязательных файлов целевой архитектуры проверяется до публикации.

`UPDATES.json` остаётся единственным подписанным источником релизных метаданных. В том же документе хранится `artifacts` с записью для каждого поддерживаемого имени архитектуры: безопасное имя файла, URL, `size_bytes`, `sha256` и подписанный `unpacked_size_bytes`. Ed25519 подписывает весь JSON; публикация проверяет фактические длину и SHA-256 каждого архива до подписи и после загрузки опубликованных assets.

Единая функция в `platform/openwrt/manifest.sh` сопоставляет локальную архитектуру с каноническим ключом и возвращает нормализованную выбранную запись (`filename`, URL, размер и SHA-256). `release.sh` получает запись только через неё; `release_state.sh` сравнивает receipt через тот же accessor digest, без прямого обращения к `artifact.sha256`. Bootstrap выполняет тот же выбор до загрузки движка, так как он запускается раньше установленной библиотеки; его контракт и архитектурное отображение проверяются теми же тестами. Неизвестная архитектура, отсутствующий ключ, неверная запись или небезопасный URL завершают операцию с ошибкой и не приводят к загрузке чужой архитектуры. Поле `artifact` применяется только когда `artifacts` полностью отсутствует. Если per-arch карта присутствует, но повреждена или не содержит целевую архитектуру, откат к `artifact` запрещён.

### Переход

Первый релиз с новой картой включает и семь per-arch записей, и прежнее поле `artifact` с полным архивом. Старый установщик продолжает выбирать `artifact`; новый установщик выбирает per-arch запись. Это единственный переходный релиз с полным архивом. Следующие манифесты могут содержать только `artifacts`.

Следствие выбранной политики: клиент старого поколения, пропустивший переходный релиз, не прочитает последующие per-arch-only манифесты; его обновление потребует ручного восстановления. Это ограничение сознательно принято пользователем вместе с выбором fallback только на один релиз. Переходный релиз должен явно отмечаться в release checklist и миграционной документации.

Manifest reader, bootstrap `install.sh`, основной `release.sh`, receipt/installed-state validation, подпись и публикация принимают старый legacy-only документ, переходный документ и per-arch-only документ. При наличии карты digest выбранного архива сохраняется в installed receipt; receipt не должен безусловно сравниваться с отсутствующим после перехода `artifact.sha256`.

## Загрузка и транзакционная установка

Порядок для bootstrap и штатного `install_release(tag)`:

1. Получить JSON и подпись по существующему доверенному каналу, проверить подпись и проверить имя тега/платформу.
2. Выбрать единственную запись целевой архитектуры (или legacy `artifact`, только если карты нет). Проверить URL, имя файла, digest и объявленные размеры.
3. До загрузки проверить суммарную оценку пика: `archive + target staging + bootstrap engine + tar index + safety reserve`. Сравнить её и со свободным местом целевого tmpfs (`df`), и с текущим `MemAvailable`, а не с `MemTotal`: занятая приложениями и системой память уже исключена из `MemAvailable`. Для per-arch записи оценка берётся из подписанных размеров плюс измеренные верхние границы engine/index и reserve; фактические значения сверяются после получения архива. Для legacy-манифеста без распакованного размера разрешено скачать только после проверки бюджета известной части; после checksum и безопасного чтения metadata, но до распаковки, повторно проверить оставшийся бюджет по фактическим размерам. При каждом последующем этапе проверять остаточный пик с учётом уже занятого скачанным архивом/engine/index tmpfs и уменьшившегося `MemAvailable`. Если любой расчёт не помещается, остановиться до изменения установленного payload или остановки служб.
4. Скачать один архив непосредственно во временный файл рабочего каталога. Частичная/оборванная загрузка удаляется, установка не меняется. После загрузки проверить фактические длину и SHA-256. До успешной проверки digest архив не распаковывается и ни один его файл не копируется в активную установку.
5. Проверить tar entries, пути, типы и цели ссылок существующими средствами, совместимыми с BusyBox/OpenWrt. Повторно использовать уже доступные результаты там, где это просто; не добавлять общий кэш индекса или сложную передачу состояния между bootstrap и `install_release` ценой надёжности или сопровождения.
6. Распаковать проверенный архив один раз в изолированный tmpfs staging. Затем проверить фактический объём staging и свободное место overlay для новой версии, backup/rollback и служебных файлов до остановки службы.
7. Продолжить существующую транзакцию `install_release`: сохранить пользовательские конфигурации и состояние по текущим правилам, остановить службы только после всех preflight-проверок, применить payload и receipt атомарно, проверить post-install readiness и подтвердить транзакцию. При ошибке использовать существующие rollback и startup recovery.

Staging остаётся в tmpfs: перенос в overlay повышает требования к flash и ломает существующий бюджет rollback; распаковка непосредственно поверх активной версии не допускается. Не добавляются параллельные пути install/update/reinstall: Dashboard reinstall и обычное обновление продолжают вызывать тот же `install_release(tag)`.

Bootstrap и обычное обновление должны переиспользовать уже скачанный файл архива в рамках одного запуска и не создавать лишнюю полную копию. Небольшая извлечённая копия shell-движка остаётся необходимой, чтобы запустить транзакцию до установки нового payload; её объём и временные metadata входят в пиковый бюджет.

Предварительный бюджет учитывает одновременно находящиеся в tmpfs архив, staging, извлечённый engine, индекс, служебные временные данные и safety reserve. Проверяются и текущее `MemAvailable`, и свободное место конкретного tmpfs; большое значение `df` не означает наличие физической RAM. При изменении `MemAvailable`/свободного места между проверками установка прекращается до остановки служб. Overlay preflight по каждому целевому пути также остаётся до мутации. Фактический распакованный размер сверяется с манифестом и выбранными entries, чтобы подпись не заменяла проверку содержимого.

## Сохранение поведения и совместимости

- Сохраняются конфигурации и исключённые из bundle пользовательские каталоги; устанавливаемые файлы получают прежние режимы и root ownership.
- Остаются текущие проверки безопасных путей, типов entries и целей ссылок; выбор архитектуры сужает множество допустимых файлов, но не ослабляет эти проверки.
- В per-arch payload сохраняется вся общая часть OpenWrt rootfs и адаптированный upstream z2k runtime.
- Архитектурные соответствия совпадают с текущими OpenWrt/Go ABI mappings, включая `mips`/`mipsel` soft-float и исключение неподдерживаемого `mips64le`.
- Существующие OpenWrt-адаптеры и их точки входа не заменяются и не переписываются; меняются только выбор/состав артефакта и необходимое чтение манифеста.
- Подписывается один `UPDATES.json`; отдельные APK, отдельные манифесты по архитектурам и новая схема транзакций не вводятся.

## Область изменений

Ожидаемые production-компоненты: `scripts/openwrt/build-release.sh`, `stage-rootfs.sh`, `rootfs_bundle.py`, `controlled_release.py`, `sign_release.py`, `publication_policy.py`, `publish_release.sh`, bootstrap `install.sh`, `platform/openwrt/release.sh`, а также workflow CI/release. Набор точных изменений уточняется планом после ревью этой спецификации.

Тесты должны проверять build/bundle membership всех трёх бинарных деревьев для всех семи архитектур и отсутствие чужих архитектур в собранном и установленном target rootfs; вычисление, подпись, проверку и публикацию всех digest; legacy-only, transition и per-arch-only манифесты; неверную/отсутствующую архитектуру; проверку checksum до распаковки; прерванную загрузку; 128/256-МБ профили с учётом текущего `MemAvailable`; ограниченный tmpfs; недостаточный overlay; bootstrap; обычное обновление; переустановку из Dashboard; rollback и startup recovery после сбоев питания. Сценарии должны подтверждать одинаковый выбор архитектуры, digest и транзакционное поведение во всех четырёх путях.

## Измерение и критерии приёмки

Для baseline и новой реализации записать по всем семи архитектурам: сжатый размер, выбранные распакованные байты, совокупный пик tmpfs и физической RAM (архив + staging + engine + index + reserve с учётом исходной занятой памяти), overlay до/после, elapsed install time. Отдельно подтвердить на реально запущенном OpenWrt с лимитом 128 МиБ, что установка доходит до readiness; синтетические тесты профилей 128/256 МиБ покрывают отказные границы, но не заменяют этот прогон. Проверить также, что сетевой запрос роутера скачивает только выбранную архитектуру.

Измеренный baseline опубликованного архива `openwrt-rootfs.tar.gz`: 77 632 341 байт (74,04 МиБ), SHA-256 `7f2385e0f589d26207cf9b36f6f0c15f4552e4474bbcf7cdc07e4d63eb792000`. Текущий архив содержит 193 983 311 байт regular payload для всех архитектур. Повторная детерминированная tar/gzip-упаковка фактических опубликованных entries с сохранением общей части и исключением шести чужих архитектур дала кандидаты 13 133 474–14 129 940 байт (12,53–13,48 МиБ) для одной архитектуры: оценочное уменьшение скачивания на 81,8–83,1% против полного архива. Это измерение перепаковки текущего архива, не результат будущей сборки.

Распакованный выбранный payload вместе с общей частью по текущему архиву составляет 34 593 919–39 169 435 байт (32,99–37,35 МиБ). Нижняя оценка одновременных данных `архив + распакованный payload` уменьшается с 107,03–111,39 МиБ до 45,52–50,15 МиБ. Она не включает runtime процесса, временный индекс, служебные данные и резерв; итоговый бюджет и пиковые значения должны подтверждаться измерением новой установки.

В окружении доступен QEMU full-system для x86_64 с KVM, поэтому обязательный end-to-end прогон выполняется на настоящем OpenWrt guest с `-m 128M` и `-m 256M`, с ограничением tmpfs/overlay и измерением guest `MemAvailable`, tmpfs, overlay и elapsed install time. Это реальный запуск BusyBox/OpenWrt installer, но не физический роутер; отчёт так и маркирует результат. Для остальных шести архитектур фиксируются реальные release bundle размеры и membership, а общие отказные ветви покрываются тестами. Если физический роутер доступен, его замер добавляется отдельно и не смешивается с QEMU результатом.
